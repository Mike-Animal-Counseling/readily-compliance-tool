# Readily 实施交接

[English](PLAN.md)

目标是让第三方通过版本化 API 上传政策、评估问卷、复核答案。每条关键结论能点回当时所用的政策版本、页码、原句或表格单元。原有工作区继续作为参考应用。

起点：已有上传、问题提取、检索、答案草稿、审核和 CSV 导出。沿用现有 Next.js 入口和自研 PostgreSQL / pgvector 方向。开工先核对默认分支、现有迁移、入口和测试。

## 实施顺序

1. **解析与版本。** 用当前解析和检索做对照。优先评估 Docling，在有资源与时限约束的 worker 中输出条款、段落、表格和出处。测试扫描、跨页表格、嵌套条款和例外。保留表头、行列、页码、原文坐标。文档、解析器、embedding 和索引都带版本，评估固定使用同一证据快照。新索引完成校验后原子激活。
2. **完整父块。** 子块按条款边界切分，300–600 tokens 为起点。索引子块，命中后按租户范围内的「文档版本 ID + 父块 ID」先归并，再选前 K 个不同父块。每个父块只读取一次、只占一个返回名额。初版按组内最佳子块排名，保留全部命中位置。候选不足时可从有界子块池继续取不同父块。不同版本或文档独立处理。同一父块过长时按子条款或表格分批读完，保留表头和原文坐标。跟随显式条款引用并复用已读父块。关键例外或引用无法核对时进入复核。
3. **混合检索与答案。** 统一版本化的服务端 embedding。在租户、快照与生效期范围内做条款号精确匹配、PostgreSQL 全文排序与 pgvector，通过 RRF 融合。重排及跨政策拆问分别做对照。每条关键结论关联允许的证据 ID，服务端校验出处。输出区分证据支持、证据不足及需要人工复核，审核状态和审核修改单独记录。
4. **第三方接入。** 交付 OpenAPI、鉴权与幂等契约和独立 TypeScript 示例，覆盖上传、状态、评估、原文定位及复核。租户身份由服务端凭据决定，文件、任务、缓存、快照与下载一致授权。限制上传、并发和开销。把原文、索引及缓存纳入数据保留和删除流程，明确供应商数据流。

## 验收与发布

- 三个子块命中同一父块只返回一个完整父块，保留三处命中。长父块、跨页表和例外完整处理。政策换版后，已有报告的引用仍指向原快照。证据不足或关键依赖缺失时有明确状态。
- 20–30 条用于初始对照，发布用独立留出集。候选目标为证据切块覆盖率至少 90%、引用准确率至少 95%、Recall@5 较基线相对提升 20%、证据支持率相对提升 15%。先冻结指标定义和可行门槛，分开测条款召回、命中后的条件覆盖、延迟和成本。
- 通过旧工作区回归、独立客户端 E2E 和多租户隔离。并行建索引后灰度激活，演练按租户回切与恢复。用公开或合成资料开工，获准使用的真实资料留在私有验证环境。
- 第一批交付结构解析、父块去重与版本化证据契约。按仓库规范拆批并保留测试证据。
